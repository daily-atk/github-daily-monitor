## 1. 定位、目标用户、核心卖点

### 1.1 项目定位（一句话）

> **给普通人的每日 GitHub 实用项目日报**——别人推荐"开发者觉得酷"的项目，这里推荐"普通人真能用上"的工具，并且每天自动更新、同一项目 30 天不重复。

三句话展开：

- 对**读者**：一个每天打开就能看的中文网页，告诉他今天有什么能改善学习/生活/效率/健康/财务的新工具。
- 对**开发者**：一个零依赖、可自托管、可配置的日报生成引擎，可按需接 AI 润色。
- 与竞品的差异：HelloGitHub/GitHubDaily 是**人工精选、面向开发者**；本项目是**自动更新、面向普通人**，且"仓库是引擎、Pages 是产品"双形态。

### 1.2 目标用户（按优先级）

| 优先级 | 人群 | 他们的问题 | 触达渠道 |
|---|---|---|---|
| P0 核心 | **想用工具改善生活但不写代码的人** | 不知道有什么好工具，也看不懂技术社区 | 小红书、知乎、即刻、少数派、公众号 |
| P1 次核心 | **效率爱好者 / 自托管玩家** | 想要可掌控、可定制的信息源 | V2EX、掘金、Reddit、HN |
| P2 扩展 | **内容创作者 / 资讯号** | 缺稳定的选题素材 | Twitter/X、知乎、Newsletter |

> 提醒：虽然代码受众在 GitHub，但**星标主要来自 P1**；P0 带来的是访问量和传播。双线并行时，中文社媒做 P0（拉访问），技术社区做 P1（拉星标），分工不要混。

### 1.3 核心卖点（对外统一口径，三句话背下来）

1. **视角唯一**：专注"对普通人有用"，而不是"技术上很酷"——这是和所有竞品最大的不同。
2. **零门槛 + 可持续**：有在线日报每天自动更新（打开网页就能看），也有零依赖脚本可自己跑；30 天去重、领域配额避免刷屏。
3. **透明可控**：纯 Python 标准库、MIT 许可、可选 AI 且默认关闭、数据只存本地不上传。

**禁用话术**：不要说"保证每天 10 个精品"（项目定位是宁缺毋滥）、不要主动求 star（把"愿意试用/提 issue"放前面）。

## 2. README 与示例展示（转化入口，优先做）

这一节决定"看到的人会不会留下"。当前有 3 个必须修的点：

### 2.1 修 README 首屏（最高优先级，10 分钟）

- **把不可点击的 Demo 链接改成真链接**：README 第 41 行现在是
  `在线 Demo：部署 GitHub Pages 后访问 `https://daily-atk.github.io/github-daily-monitor/`（配置见下文）。`
  改成醒目的可点击行，例如：
  `**在线看今日日报** → [daily-atk.github.io/github-daily-monitor](https://daily-atk.github.io/github-daily-monitor/)（每天 20:00 自动更新）`
- **首屏加一句价值主张**：在标题下、快速开始前，用一句加粗话说明"给普通人的每日实用项目日报"（现在开头偏功能描述，缺"为什么关心"）。
- **加"不用命令行"的入口**：把"双击 运行日报.bat"的截图或提示往首屏提，降低 P0 用户的心理门槛。

### 2.2 补 Release v0.1.0（15 分钟）

发布清单里列了但一直没做。操作：

```bash
cd /d/WorkBuddy产出/github-daily-monitor
git tag -a v0.1.0 -m "首个公开版本：自动日报 + 去重 + 可选 AI 润色"
git push origin v0.1.0
```

然后用 `gh release create v0.1.0 --generate-notes` 生成 Release 说明，补上三条：能做什么、和竞品的区别、怎么一键开始。Release 是很多人判断"项目是否认真维护"的信号。

### 2.3 打开 Discussions（2 分钟，反馈收集的地基）

`gh repo edit daily-atk/github-daily-monitor --enable-discussions`，然后建三个分类：

- `Ideas`（功能建议）
- `Show and tell`（谁用日报做了什么）
- `Q&A`（使用问题，替代 issue 里的问答噪音）

### 2.4 示例展示增强（可选，效果明显）

- 在 README 首屏截图下再放一张"某期日报的局部特写"，让人 3 秒看懂产出长什么样。
- 首页归档页（`site/index.html`）加一行说明"每日 20:00 自动更新，可按日期回看"。
- 长期：给报告页加 Open Graph 标签，这样转发到微信/Twitter 时有标题和缩略图，点击率差别很大。

## 3. 内容发布（把已有文案按节奏发出去）

`docs/launch/` 和 `docs/promotion/` 已备好 10+ 渠道文案，**不要重写**，按下面的顺序和节奏投放。原则：**一次只主攻一个渠道**，观察 2–3 天再发下一个，避免同一天刷屏显得像营销机器。

### 3.1 中文首发序列（拉访问量 + 首批星标）

| 顺序 | 渠道 | 用哪份文案 | 关键动作 | 预期 |
|---|---|---|---|---|
| 第 1 站 | **V2EX · 分享创造** | `docs/launch/v2ex-post.txt` | 反馈最快，先验证表达是否清楚；作者在场认真回复每一条 | 首批真实反馈 + 早期星标 |
| 第 2 站 | **少数派** | `docs/launch/sspai-post.md` | 根据 V2EX 反馈改一版再投，图文要完整 | 高质量长尾访问 |
| 第 3 站 | **HelloGitHub** | `docs/promotion/hellogithub.md` | 按官方模板投稿，接受周期长，早投早排队 | 权威背书 + 星标跃升 |
| 第 4 站 | **掘金 / 开源中国** | `docs/promotion/juejin-oschina.md` | 技术长文，强调"零依赖 + 可选 AI" | 开发者星标 |
| 长期日更 | 小红书 / 知乎 / 即刻 | `xiaohongshu-daily.md`、`zhihu-daily.md`、`jike-daily.md` | 把每期日报二次加工成短内容，正文不放外链（引流到主页） | 持续曝光 |

> 国内访问提醒：GitHub Pages 在国内可能不稳。文案里同时给"本地双击 bat 运行"的兜底，中期考虑 Gitee Pages 镜像（`juejin-oschina.md` 里已有镜像步骤）。

### 3.2 英文序列（拉开发者星标，高质量但慢热）

| 顺序 | 渠道 | 用哪份文案 | 关键动作 |
|---|---|---|---|
| 第 5 站 | **Hacker News · Show HN** | `docs/promotion/hacker-news.md` | 标题诚实不夸张；发布后 2 小时内守在评论区回复所有问题，这是 HN 的隐形规则 |
| 第 6 站 | **Reddit** | `reddit-subreddits.md` | **一次只发一个 sub**，先 r/Python；不要让人集中 upvote（会被封） |
| 第 7 站 | **Twitter/X** | `twitter-thread.md` | 7 条 thread，配一张日报截图 |
| 第 8 站 | **Product Hunt** | `product-hunt.md` | 门槛最高（需 logo/gallery/hunter），放最后，等前面有口碑再做 |

### 3.3 每周 2–5 小时怎么分配（现实可行版）

```
第 1 周：修入口(0.5h) + 打 Release(0.3h) + V2EX 发布与回复(2h)
第 2 周：少数派投稿(1.5h) + HelloGitHub 投稿(0.5h) + 回看数据(0.5h)
第 3 周：掘金长文(1.5h) + HN 发布并守评论(2h)
第 4 周：Reddit 单 sub(1h) + Twitter thread(0.5h) + 开始日更模板(1h)
之后每周：日更内容 1–2h + 回复互动 1h + 看数据 0.5h
```

## 4. 社区传播（让传播可持续，而非一次性）

- **作者在场**：每个平台发布后的前 24 小时，尽量回复每一条评论。早期项目的"作者亲自回复"比文案本身更能建立信任。
- **回答而不是硬推**：在 V2EX、知乎相关问题下，先给出有价值的回答，自然带出项目；不要在不相干群里丢链接。
- **借势同类项目**：在 HelloGitHub、GitHubDaily 的投稿/推荐渠道投自己；也可以关注"每日开源"类账号的转载机制。
- **给贡献者台阶**：README 已有 CONTRIBUTING，推广时主动说"欢迎提 issue 说你想要监测哪些关键词"——把读者变成参与者，星标和讨论会自然增长。
- **不做的四件事**（红线）：不买星、不刷榜、不群发广告、不同一天全网铺同一段话。

## 5. 用户反馈收集（把流量变成产品力）

1. **入口**：开启 Discussions（见 2.3），README 的 FAQ 下加一句"有问题去 Discussions 或提 Issue"。
2. **主动问**：每篇发布文案结尾统一放一个具体问题，例如"你最希望每天看到哪类工具？"——比"欢迎反馈"有效得多。
3. **归类**：每周把反馈分三类记到 `docs/FEEDBACK_LOG.md`（新建）：`质量误报` / `功能请求` / `使用困难`。质量误报优先修（这是产品生命线）。
4. **闭环**：修复后在该 issue/discussion 回复"已修复，感谢"，并考虑发布小版本 Release。被采纳的建议要公开致谢——这是最好的口碑素材。
5. **隐私**：反馈里若有人贴 token，立即提醒删除；不要在公开回复里引用任何凭据。

## 6. 效果跟踪（用数据决定下一步投哪）

### 6.1 指标体系（按优先级）

| 层级 | 指标 | 怎么看 | 目标节奏 |
|---|---|---|---|
| 北极星 | GitHub Stars | 仓库页 / `gh api` | 每周记录增量，看哪次发布带来跃升 |
| 传播 | Pages 访问量 | 加隐私统计（见 6.2） | 判断中文社媒是否真的导流 |
| 参与 | Issue + Discussion 数、评论质量 | GitHub | 真实反馈比 star 更有价值 |
| 采用 | Fork 数、"我自托管了"的反馈 | GitHub / 评论 | 判断 P1 用户是否行动 |
| 内容 | 各平台阅读/点赞/收藏 | 平台后台 | 找出 ROI 最高的渠道，加大投入 |

### 6.2 加一个轻量统计（30 分钟，强烈建议）

没有数据就只能靠感觉。给报告页加一个**隐私友好**的统计（如 Plausible / 简单自托管计数），只统计访问量和来源，不收集个人信息。加好后每周记一次：

```
| 周次 | Star | 新增 Star | Pages PV | 主要来源 | 本周发布渠道 | 备注 |
|---|---|---|---|---|---|---|
| W1 |  |  |  |  | V2EX |  |
```

坚持 4 周，就能看出"哪个渠道值得长期投入、哪个可以停"。

## 8. 三个月目标（可衡量）

- **Star**：0 → 200+（主要来自 V2EX / HelloGitHub / HN 三次首发）
- **Pages 月访问**：建立统计基线后稳步增长
- **真实反馈**：Discussions + Issue 累计 20+ 条，其中至少 5 条转化为改进
- **内容资产**：沉淀 4 周日更模板，形成可持续的内容飞轮

> 数字是方向不是承诺。如果某个渠道明显无效（发了没人看），按数据停掉，把时间投给有效的那个——这比"每个平台都发一遍"更重要。
