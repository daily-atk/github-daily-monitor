# 少数派重写结构（不是终稿）

> 用途：按这个结构，用你自己的真实经历重写。**不要把这份提纲直接投出去。**
> 原因：少数派 AI 规则要求作品实质部分由人创作，并披露 AI 使用的方式、范围和工具名。这份只是结构建议，不是成稿。

---

## 一、先换标题

不要用「一个零依赖小工具的诞生」这种产品发布口吻。选一个“经验/踩坑/场景”型标题：

1. 朋友问我 GitHub 有什么好用的，我打开了 Trending，然后沉默了
2. 我给不写代码的朋友做了份 GitHub 日报，最后自己也在用
3. 从 120 条候选到 4 个推荐：我给普通人做 GitHub 日报踩过的坑
4. 不写代码的人，怎么从 GitHub 找到真正能用的工具？
5. 我做了个只推荐「普通人能用」的 GitHub 日报，聊聊筛选这件事

推荐 1 或 3：有具体场景，像个人经历，不像产品广告。

---

## 二、新结构（7 节）

### 第 1 节：一个具体场景（300–400 字）

**目的**：让读者先进入你的真实处境，而不是先看到产品。

写什么：

- 朋友是在什么场景下问你的？（微信？饭桌？他最近想解决什么问题？）
- 他原话怎么说？尽量写一句真实对话。
- 你打开 Trending 看到了什么？为什么觉得“没法直接推荐”？
- 他真正想要的是什么？（“今天能装的”而不是“技术有多新”）

不要写：

- 不要先介绍项目、不要先讲“我做了个工具”。
- 不要用“随着……”“在当今……”这类开头。

开头示例（只学语气，不要照抄）：

> 朋友在微信上问我：GitHub 上是不是有很多好用的小工具，给我推荐几个。我打开 Trending，看了几秒，有点不知道从哪说起。

### 第 2 节：我一开始做错了什么（400–500 字）

**目的**：先承认失败，建立可信度，而不是一上来讲成功。

写什么：

- 第一版是怎么做的？（按关键词搜、按 star 排）
- 推了哪些不该推的？（举 1–2 个具体项目，说明为什么不适合普通人）
- 有没有被朋友吐槽/卸载/不用？写一个具体反馈。
- 你当时怎么意识到“这不是筛选，是搬运”？

不要写：

- 不要写成“我设计了一个完美的系统”。
- 不要只讲规则，要讲规则是被什么问题逼出来的。

### 第 3 节：三个具体改动（700–900 字）

**目的**：这是全文的技术核心，但要用“问题 → 改动 → 结果”讲，不要写成配置说明。

建议只写三个，每个 200–300 字：

1. **把开发者基础设施挡在门外**
   - 原来：框架、SDK、数据库也会进来。
   - 问题：朋友点进去第一步就劝退。
   - 改动：项目名/描述/topics 命中 SDK、library、framework、CLI、Docker 等就扣分或过滤。
   - 结果：推荐里不再出现“给开发者用的工具”。

2. **去重和领域配额**
   - 原来：同一项目连续几天出现；生活类占满整页。
   - 问题：自己看着烦，朋友也觉得“怎么又是这个”。
   - 改动：推荐过 30 天冷却、见过没选 7 天冷却、每领域最多 3 个。
   - 结果：每天更像“新的一份”，而不是昨天的复读。

3. **搜索精度的本地校验**
   - 原来：搜 habit tracker 会冒出 habitat。
   - 问题：名字像、用途完全无关。
   - 改动：搜索词里的实词必须真的出现在结果里（本地短语校验）。
   - 结果：误匹配少了大半。

每节尽量有一个**具体数字或例子**：120 条候选 → 4 个推荐；某个项目被连续推了 5 天；某个领域占了 8/10。

不要写：

- 不要贴大段代码；最多一行伪代码或一个命令。
- 不要把 `config.json` 的每个字段解释一遍。

### 第 4 节：朋友后来怎么用（300–400 字）

**目的**：这是最能打动编辑和读者的部分——真实使用，而不是功能列表。

写什么：

- 他最后装了哪个？（点名一个具体项目）
- 用了几天？留下了吗？为什么？
- 有没有一个“失败案例”：装了又卸、或者根本没用起来？
- 你从他身上观察到什么？（普通人真正在意的是“手机能不能用”“要不要配置”“免费吗”）

不要写：

- 不要编造“朋友说太好用了”这种空话。
- 不要只写成功案例；一个失败案例更可信。

### 第 5 节：为什么又做了程序员版（300–400 字）

**目的**：解释第二个版本，但不要写成功能清单。

写什么：

- 哪个开发朋友、在什么场景下说“我们恰恰想看框架和 SDK”？
- 他们的真实需求是什么？（技术选型、跟热点、看今天什么涨得快）
- 两版的差异用一句话说清：同一套代码，两种读者，两份配置。
- 你做了什么取舍？（数据源换成 Trending、按新增 star 排、深色主题）

不要写：

- 不要列“支持 8 个技术方向、25 条 Trending”这种参数表。
- 不要把它写成第二个产品发布。

### 第 6 节：我没做好的地方（300–400 字）

**目的**：主动说局限，降低“软广”感，建立信任。

写什么（挑 3–4 个真实的）：

- 筛选靠规则，不是人工把关，质量有起伏。
- 不保证每天 10 个；某天只有 4 个。
- 不接 AI 时文案很干（截图里那句“主要围绕 blazor、blazor-server”就是例子）。
- GitHub Pages 在国内可能打不开；这是现实限制。
- 推荐错了，欢迎到 Issue 里说。

不要写：

- 不要用“宁缺毋滥”当万能借口；要给出具体数字和例子。
- 不要把所有问题都归因于“用户网络”。

### 第 7 节：怎么用 + 结尾（200–300 字）

**目的**：给入口，但不把文章变成教程。

写什么：

- 一句话：普通人版看哪里，程序员版看哪里（各一个链接）。
- 一句话：想本地跑，Windows 双击 bat，macOS/Linux 跑 run.sh；不想折腾就看网页。
- 结尾回到朋友/初衷：一开始只想给不写代码的朋友看，后来开发朋友也要，就有了两个版本。
- 作者披露：这是我做的项目。
- **AI 使用披露**（如果你用了 AI 辅助写作/润色）：
  > 说明：本文在结构整理和文字润色过程中使用了 [工具名]，文中经历、数据与观点由作者本人提供并核对；AI 未用于生成核心经历或数据。

不要写：

- 不要放 Fork / Actions / 配置字段的完整教程（可以一句话带过或另写一篇）。
- 不要反复放同一个链接。

## 三、必须删掉/改掉的东西

| 当前稿子里的内容 | 怎么处理 |
|---|---|
| 开头「26/32」 | 删掉；如果是平台评分，不要放进正文 |
| 「……DeepSeek、通义、本地模型都行几件得说清楚的事」 | 这是断句；恢复成「都行：」+ 代码块 + 新标题「几件得说清楚的事」 |
| 「关于 AI，说两句」整节 | 压缩成 2–3 句：产品 AI 可选、默认关闭；不要写成功能广告 |
| 「怎么用」里的 Fork/Actions/配置字段 | 压成一段，或删掉；正文只留“看网页/本地跑”两条 |
| 多个 GitHub/Pages 链接 | 正文只留 1 个仓库链接 + 1 个 Demo 链接 |
| 「一个零依赖小工具的诞生」 | 换成经验/场景型标题 |
| 产品参数（25 条、8 个方向） | 删掉或改成一句“按新增 star 排” |

## 四、首发与重复提交检查

- 这篇（或高度相似的版本）有没有在 V2EX、知乎、公众号、小红书、个人博客、GitHub 上发过？
- 如果发过，是否满足少数派的“首发”三条：
  1. 发布渠道是你个人名义的网站/账号；
  2. 发布日期距提交未满 7 天；
  3. 没有获得任何金钱/非金钱报酬。
- 三条缺一条，就不算首发。**不要为了绕过规则删掉旧文再投**；先等 7 天，或写一篇新的。
- 如果最近已经投过多次，先停一段时间，不要连续重投。

## 五、投稿前自检

- [ ] 标题是经验/场景型，不是产品发布型
- [ ] 第 1 节有具体对话/场景，不是“随着……”
- [ ] 第 2 节承认了一个具体的失败/误推
- [ ] 第 3 节每个改动都有“问题 → 改动 → 结果”
- [ ] 第 4 节有一个真实使用案例（最好含一个失败案例）
- [ ] 第 6 节写了 3 个以上真实局限
- [ ] 正文链接不超过 2 个
- [ ] 没有 Fork/Actions 完整教程
- [ ] 没有「26/32」和断句
- [ ] 截图与文中数字一致（写 4 个就用 4 个那天的截图）
- [ ] 图片已上传到少数派，不用 raw.githubusercontent 外链
- [ ] 已确认首发条件
- [ ] 已披露 AI 使用（如有）
- [ ] 最近没有频繁重投

## 六、最省力的写法

1. 先把第 1、2、4、6 节用手机备忘录写出来——这四节全是你的真实经历，AI 帮不上忙，也最像“人写的”。
2. 再把第 3 节的技术改动补进去，每段控制在 200–300 字。
3. 最后写第 5、7 节，收尾。
4. 写完后放一天，第二天朗读一遍，删掉所有“随着/值得一提的是/说白了”这类 AI 常用过渡词。
5. 投稿只投一次，等审核。
